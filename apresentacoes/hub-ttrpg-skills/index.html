Como o hub TTRPG foi construído com skills de IA

Otimizando desenvolvimento de apps e de conteúdo com skills, scripts facilitadores e memória de projeto.

Abertura, um minuto. Isto não é uma palestra sobre prompts: é o relato de um sistema construído para a IA trabalhar como parte do projeto, com manual versionado, ferramentas próprias e memória entre sessões. O domínio é RPG de mesa, mas o que interessa aqui é a infraestrutura que nasceu dele. São cinco atos em meia hora: problema e arquitetura, skills, scripts e moldes, casos reais e lições transferíveis. Todos os números citados foram contados nos repositórios nesta semana, com busca de arquivos e histórico do git, nada é estimativa de memória. Setas navegam e a tecla S abre estas notas. Um aviso de método: o estudo de caso é verificável, porque os arquivos citados estão no vault e nos repositórios e podem ser abertos ao vivo se alguém quiser conferir uma afirmação específica. Transição: comecemos pelo problema que esse sistema resolve.

Ato 1 · O problema

O problema: a IA esquecia tudo a cada sessão

Conteúdo disperso

Campanhas, regras, PDFs e dois webapps em repositórios separados, sem mapa comum.

Tarefas repetitivas

Converter, narrar, sincronizar, migrar: trabalho manual, um repo e um comando por vez.

Qualidade sem padrão

Sem molde, cada ficha, ameaça ou aventura nascia num formato.

O gargalo nunca foi a IA saber responder. Era contexto: ela não sabia onde agir, não conhecia as convenções, não tinha ferramenta pronta e não lembrava a sessão anterior. São quatro faltas, e cada ato desta apresentação responde a uma delas. Exemplos concretos: reexplicar o formato de uma ficha, lembrar em qual dos oito repositórios está um arquivo, reconstruir de cabeça o comando certo de migração. Nenhum desses custos aparece num orçamento, mas somados eles comem a sessão de trabalho. A pergunta que guiou tudo foi: como fazer esse contexto morar no projeto, e não na cabeça de quem pede? Um custo invisível merece nome: quando o agente edita no repositório errado, o erro só aparece depois, ao sincronizar ou publicar, e o retrabalho custa mais que a tarefa original. Transição: a resposta começa pela arquitetura.

Ato 1 · Arquitetura

A resposta: um hub que funciona como monorepo virtual

Obsidian na raizvault único, wikilinks entre todos os repos
→

→
Clones gitignoredcada filho com git próprio

Quem abre a raiz, pessoa ou IA, enxerga o projeto inteiro de uma vez: o bootstrap.sh monta o workspace a partir do manifest, e o sync_repos o mantém atualizado.

A decisão central foi não fundir tudo num repositório só, nem deixar tudo solto. O hub é uma camada fina de orquestração sobre repositórios independentes: cada filho mantém histórico e ritmo próprios, e o hub não versiona clones. O manifest é a declaração única dos filhos; bootstrap e sincronização leem dele, e os slides de cada um detalham isso adiante, sem repetir aqui. O Obsidian aberto na raiz enxerga o conjunto como um vault só, com wikilinks cruzando repositórios. Até a exceção é declarada: Outros RPGs mora no hub porque é conteúdo dele. Insistam na palavra virtual: não há um repositório gigante escondido, há repositórios normais mais uma camada de declaração e roteamento por cima, que pode ser removida sem quebrar nenhum filho. Transição: quem são os moradores desse mapa?

A leitura importante da linha do tempo não é a data, é a aceleração. O projeto mais recente é o que nasceu mais rápido e mais testado, porque herdou skills, moldes, scripts e gates dos anteriores. Essa é a tese da apresentação demonstrada pelo próprio histórico: cada camada nova reaproveita a infraestrutura das anteriores. Os quatro números da grade são os que valem guardar: skills, conteúdo, testes e produtos publicados; o restante da apresentação explica como eles se produzem mutuamente. A contagem veio de busca de arquivos e de git log em cada repositório. Metodologia em uma frase: skills contam-se pelos arquivos canônicos, conteúdo pelos Markdown fora dos modelos, testes pelos arquivos de teste dos dois apps, tudo na mesma data de medição, para os números serem repetíveis por quem quiser auditar. Ato 2 · Skills

O que é uma skill: procedimento versionado, carregado sob demanda

---
name: shadowdark-ameaca
description: >-
  Criar ou editar ameaças Shadowdark a partir de AmeacaModelo.md
  (ficha avulsa, verbete Bestiário, Equilibrar Encontros, blocos NV,
  chefes). Use quando o pedido for monstro, encontro, orçamento NV
  ou ficha de ameaça Fantasia/Shadowdark.
---

# shadowdark-ameaca
## Quando usar cada modo …   (corpo: passos, guardrails, exemplos)

A description é o gatilho: é ela que faz o agente escolher a skill certa sem ninguém pedir pelo nome.

Anatomia mínima: frontmatter com nome e descrição-gatilho, corpo com procedimento. A skill é um arquivo no repositório, revisável em diff e com histórico, não um conhecimento solto num prompt de chat. Reparem na redação da descrição: ela lista os sinônimos do pedido real, monstro, encontro, orçamento, ficha, porque é escrita para casar com a linguagem de quem pede, não com o nome interno. Descrição ruim, a skill certa nunca dispara; descrição ampla demais, dispara fora de hora. E ela só é carregada quando o pedido combina: contexto sob demanda, não um prompt gigante permanente. Detalhe de ofício: o corpo da skill manda ler arquivos de referência só quando o modo escolhido exige, então exemplos longos não pesam em toda conversa, só na tarefa que realmente os usa. Transição: onde essas skills moram?

Ato 2 · Arquitetura de skills

Três camadas: canônica, proxy, symlink

1 · Canônica no filhorepos/shadowdarkrpg-fantasia/skills/shadowdark-ameaca/SKILL.md, mora com o conteúdo
→
2 · Proxy fino no hub.cursor/skills/fantasia/<slug>/, só aponta para a canônica
→
3 · Symlink flat.cursor/skills/<slug>, descoberta automática pelos agentes

Canônica é a versão oficial e completa da skill, a única que se edita. Proxy e symlink não são cópias: só apontam para ela, e o hub expõe 60 entradas no total (proxies dos filhos + 9 skills próprias), com zero duplicação de corpo.

"Não duplicar o corpo da skill no hub: o proxy só aponta para a canónica no repo filho." — .cursor/skills/README.md

Este é talvez o padrão mais reutilizável da apresentação. A skill vive onde o conteúdo vive: quem clona só o Fantasia tem as skills do Fantasia. O hub publica apenas um índice, com proxies agrupados por repositório e symlinks para a descoberta automática. Atualizou a canônica, todos os agentes veem a versão nova; divergência entre cópias é impossível por construção. Dois cuidados práticos: os caminhos dentro do proxy são sempre a partir da raiz do hub, e, se o caminho canônico não existir, o próprio proxy instrui a rodar o bootstrap daquele repositório. E o symlink não carrega conteúdo nenhum: se a canônica muda, não existe etapa de republicar o índice, o apontador simplesmente passa a resolver para a versão nova. Transição: a mesma ideia de fonte única vale para as instruções dos agentes.

Ato 2 · Multi-agente

Uma fonte, várias IAs: AGENTS.md + stubs

# CLAUDE.md / GEMINI.md / TRAE.md  (em cada repo)
@AGENTS.md
AGENTS.md

Único arquivo editável de orquestração por repo: roteamento, guardrails, catálogo de skills e comandos.

Stubs de 1 linha

Cursor, Claude, Gemini e Trae leem o mesmo conteúdo pelos seus arquivos convencionais.

Regra explícita

"Edite somente este arquivo; stubs apenas apontam para cá", escrito no próprio AGENTS.md.

Seis repositórios têm o trio completo de stubs resolvendo para o mesmo AGENTS.md. A consequência prática: trocar de IDE ou de modelo não muda o comportamento do projeto, porque a instrução é do repositório, não da ferramenta. O custo de manutenção é de um arquivo; mudou a regra, muda-se o AGENTS.md, e os stubs continuam válidos para sempre porque não contêm regra nenhuma. Há um efeito humano também: quem clona o repositório lê o mesmo manual que a IA lê, e o AGENTS.md vira a documentação de entrada do projeto. Na prática, isso apareceu quando o mesmo projeto foi aberto em ferramentas diferentes na mesma semana: o comportamento se manteve porque o manual era o mesmo, mudava só o leitor. Transição: com instruções únicas, o hub consegue rotear pedidos.

A tabela de roteamento vive no AGENTS.md do hub. Percorram uma linha inteira: no pedido "atualiza as regras no app", quem pede não diz repositório, comando nem ordem; a tabela resolve os três e ainda embute o passo de testes. Quem usa fala em linguagem natural, e o agente resolve repo, skill e comando. É a diferença entre uma IA que responde e uma IA que opera o projeto. E quando um pedido novo não casa com linha nenhuma, isso também é informação: provavelmente falta uma skill ou uma linha na tabela. A linha do BG3 mostra o outro extremo do roteamento: não é um comando, é um processo inteiro com estado, e a tabela aponta para o arquivo de estado antes de qualquer etapa ser executada. Ato 2 · Catálogo

Catálogo vivo: seis famílias de skills

Book-skills

Livros e suplementos viram skills consultáveis sob demanda.

Tabelas roláveis

*-tabelas: consultar e executar a tabela, não só ler.

Workflow de app

O ciclo dos PWAs, do desenvolvimento ao gate de entrega.

Skills que criam e governam outras skills e scripts.

Não tentem memorizar a lista; reparem nas famílias e na precedência. As tabelas roláveis transformam leitura em execução: pedir um encontro executa a tabela em vez de só mostrá-la. As skills de estilo têm hierarquia declarada, e a edição manual do autor fica acima delas. O destaque é a família meta: existe uma skill cuja função é fabricar outras a partir de livros, extraindo capítulos sob demanda em vez de despejar o livro inteiro no contexto. O sistema se expande usando o próprio sistema. Os casos concretos de cada família aparecem nos próximos atos. Em uma frase: catálogo bom não é lista longa, é lista com família, dono e precedência, para o agente saber não só o que existe, mas o que vale primeiro quando duas skills combinam com o mesmo pedido. Transição: procedimento sem ferramenta determinística ainda improvisa; entramos nos scripts.

Ato 3 · Caso: sync

Skill decide, script executa: sincronizar 8 repos num comando

# cwd = raiz do hub
./scripts/sync_repos/sync_repos.sh --status
./scripts/sync_repos/sync_repos.sh --msg hub="…" -y   # uma --msg por repo sujo
A skill (hub-sync-repos)

Lê o status, redige uma mensagem por repo, chama o CLI e apresenta o relatório.

O script (sync_repos)

Pull com rebase antes de commit e push; continua após falha parcial; relatório OK / SKIP / FAIL.

Os guardrails

Sem force push, sem tocar em .git/config; árvore suja falha o pull só daquele repo.

Antes, isto era um loop manual de git em oito diretórios, com mensagens improvisadas e o risco de esquecer um repositório. Depois, virou um pedido em linguagem natural. A divisão de trabalho é o padrão que se repete no hub inteiro: julgamento na skill, determinismo no script, segurança nas regras dos dois. A mensagem é por repositório porque um texto genérico em oito históricos diferentes seria ruído. Falha num repo não aborta os outros, mas o relatório final marca a falha. E, se faltar um clone, o próprio status sugere o bootstrap pontual. Se houver demonstração ao vivo, o comando seguro é o de status: ele não altera nada e já mostra clones faltando, repositórios sujos e o formato do relatório que a skill apresentaria antes de qualquer commit. Transição: é o bootstrap que monta esse workspace.

Ato 3 · Instalação em cadeia

Bootstrap: do clone do hub ao workspace completo

git clone …/ttrpg.git && cd ttrpg
./scripts/bootstrap.sh                        # todos os filhos do manifest
./scripts/bootstrap.sh --only bg3-fan4fun     # só um repo
./scripts/bootstrap.sh --skip-pull            # só clona o que falta

O mesmo repos.manifest.json alimenta bootstrap, sync e o roteamento do AGENTS: uma declaração, três consumidores.

Instalação em cadeia é o que transforma "o meu workspace" em "um workspace reproduzível": máquina nova, um clone, um comando, e os filhos estão no lugar. A peça que destrava isso é pequena, um manifest declarativo com identificador, endereço e caminho de cada filho. Adicionar um repositório ao ecossistema é adicionar uma entrada nele e um AGENTS.md; o resto da máquina passa a enxergá-lo, inclusive a sincronização quando um clone está faltando. Existe ainda o espelho para Windows, porque o workspace não podia depender de um sistema só. O manifest também é o que permite à sincronização avisar que um clone sumiu e sugerir o bootstrap daquele identificador, em vez de falhar com um caminho inexistente no meio do processo. Transição: ferramenta nova também precisa de governança.

Ato 3 · Governança

Script novo não nasce sem aprovação: a skill hub-scripts

Pararantes de gravar qualquer .py/.sh novo
→
PerguntarAskQuestion com nome, o que faz e tecnologias
→
Permanentescripts/{nome}/ versionado + catálogo atualizado
ou
Pontual/tmp, usado e apagado na mesma sessão
ou
Não criarusar CLI existente ou one-liner

Sem essa gate, todo projeto com IA vira uma pasta de scripts órfãos. Com ela, cada automação permanente tem dono, README e registro no AGENTS.

Esta skill é governança pura, e das mais importantes. Ela inverte o padrão: em vez de a IA sair criando utilitários, ela precisa justificar nome, propósito e tecnologias antes de persistir qualquer arquivo executável, e oferecer explicitamente a opção de não criar. O permanente ganha pasta própria, executável, wrappers, README e registro no catálogo do AGENTS.md, para ser descoberto pelo catálogo e não por arqueologia de pastas. O pontual não é catalogado nem commitado. E "não criar" é levado a sério: às vezes a resposta certa é um comando inline ou um CLI que já existe. A pergunta da gate tem três respostas legítimas, e a terceira é a que mais protege o projeto: automação permanente sem dono vira dívida, mesmo quando o código dela funciona bem. Transição: com as ferramentas sob controle, vejamos o que elas fazem encadeadas.

Se uma tarefa se repete, ela desce um degrau: de conversa → skill; de skill → script; de script → comando catalogado.

Cada CLI faz uma coisa e compõe com a próxima por formato, não por acoplamento. Percorram a cadeia com um exemplo real de preparação de sessão: o PDF de uma missão vira Markdown com wikilinks no vault, o texto narrável é extraído dele e o TTS gera o áudio de preparação. O caminho inverso também existe: o Markdown de um suplemento vira PDF tipográfico publicável. Reparem no pdf_translate: há revisão humana via manifest entre traduzir e gerar, o mesmo padrão de portão que aparece no BG3. A frase de fecho resume a regra de evolução de tudo o que vimos neste ato. Composição por formato também significa troca isolada: outro motor de PDF ou outra voz de narração entra na cadeia sem tocar nas etapas vizinhas. Transição: falta o molde.

Ato 3 · Modelos de conteúdo

Modelos de estrutura: a IA preenche o molde, não inventa o formato

FichaModelo.md

Ficha de personagem Shadowdark, usada pela skill shadowdark-personagem.

AmeacaModelo.md

Dois modos: ficha avulsa completa ou verbete de Bestiário enxuto; a skill escolhe, o molde fixa o formato.

AventuraModelo.md

Esqueleto por padrão, conteúdo completo só se pedido; variantes catalogadas no molde.

Equilibrar Encontros.md

Orçamento de nível (NV × nº de PJs): "encontro médio" vira conta verificável.

Templates BG3 de mesa

Fichas de desafio, inimigo, item e personagem em templates/mesa/.

Templates de registro BG3

Progresso, catálogos, estado e decisões com molde próprio.

Molde é a forma mais barata de qualidade: separa o que é formato, fixo no arquivo, do que é criação, variável a cada uso. O efeito colateral é consistência entre dezenas de arquivos escritos em sessões e por agentes diferentes. O molde também carrega decisão, não só campos: o de aventura declara que o padrão é gerar só o esqueleto, protegendo o autor de receber dez páginas quando pediu uma estrutura; o de ameaça documenta quando usar cada modo. E o último cartão adianta o tema do tracking: até a memória do projeto tem molde. Quando um artefato sai fora do padrão, a correção é no molde ou na skill, uma única vez, e não arquivo a arquivo: é assim que o padrão melhora com o uso em vez de degradar. Transição: vejamos tudo isso operando junto.

Contem os elos em voz alta: sem o contexto da campanha, a aventura nasce genérica; sem o local, o encontro não tem território; sem o orçamento, nasce desbalanceado. Neste caso, o conteúdo nunca é editado no JSON: edita-se no vault, migra-se, testa-se e publica-se. Não há sincronização automática, de propósito; a migração é um ato explícito e revisável. Os dezesseis migradores são pequenos e separados por tipo de dado, regras, ameaças, tabelas e catálogos, orquestrados por um comando único em cada app, de modo que uma falha diz exatamente qual tipo quebrou. A faixa de baixo é a qualidade virando comportamento: o gate de pré-entrega é uma skill que dispara nas palavras entregar e deploy, e a conformidade de licença virou flag de build testável. O segundo Escudo reaproveitou esse padrão inteiro. A edição direta do JSON existe só como exceção documentada de hotfix, com a mesma obrigação de rodar os testes depois; a rotina continua sendo editar no vault e migrar, nunca o contrário. Transição: o caso mais longo é o BG3.

5 skills, um pipeline

Orquestrar, pesquisar, adaptar, auditar e rastrear, cada etapa com artefato de saída.

Classificação da informação

Toda afirmação é FATO_WIKI, REGRA_DND5E, ADAPTACAO_PROJETO, INFERENCIA ou LACUNA.

Portão de decisão

Em "perguntar", o agente para e apresenta as decisões materiais; rota narrativa nunca é escolhida em silêncio.

Transformar um videogame de centenas de horas numa campanha jogável é um problema de engenharia de conteúdo. A ordem do pipeline impõe as separações: pesquisar produz um dossiê só com fatos, sem mecânica; adaptar só começa depois da decisão do autor; auditar confere fidelidade, regras e balanceamento antes da aprovação. A etapa "perguntar" é a mais incomum: a skill obriga o agente a parar, sem permissão estrutural para decidir sozinho. E a classificação da informação garante que inferência nunca se disfarque de fato. Cada etapa tem uma skill dona e um artefato nomeado. A auditoria usa uma rubrica editorial registrada, então aprovar não é uma impressão do momento: é uma decisão com critério anotado, que o tracking guarda junto do estado de cada unidade produzida. Transição: um projeto assim só anda com memória explícita.

Este é o antídoto direto para o problema do segundo slide. O trecho na tela responde em segundos onde estamos, em que etapa do fluxo, qual é o próximo passo e se há bloqueio, inclusive nomeando a skill que executa o próximo passo. O passo um é um arquivo de texto por repositório; o passo seis, um arquivo de estado de meia página. As primeiras skills úteis costumam ser duas ou três: a tarefa mais repetida, o artefato mais refeito, o comando mais esquecido. Este hub chegou ao tamanho atual por formalização incremental, uma repetição de cada vez, ao longo de meses de uso real. A ordem importa menos que começar versionado. A demanda-guia é simples de propósito: permitir checkout com Pix num produto que hoje só aceita cartão. Scrum aqui não é cerimônia decorativa; é onde a cadeia encontra limite de capacidade e dependência real. No refinamento, a skill ajuda a quebrar a história do Pix no que é API, no que é app e no que é webhook, marcando dependências e riscos. Na planning, ela não decide sozinha: monta uma proposta a partir do board, da capacidade declarada pelo time e de consultas JQL que ficam versionadas como script. A daily é leitura de exceção, não status completo: o que bloqueou, o que parou e o que ameaça o objetivo. O ponto inegociável é não criar um segundo tracking em Markdown: o estado mora no Jira. Transição: sprint planejada, começa a execução.

Na execução, a rastreabilidade é mecânica: a branch nasce ligada à história, o PR usa template e aponta de volta para o Jira. As skills de implementação são as do próprio repositório, porque a convenção de API não é a mesma do app. Quando a pipeline falha, a skill de diagnóstico lê o log e classifica a falha antes de alguém sair alterando código: erro real, teste instável ou ambiente. A avaliação de PR feita pela IA é uma pré-revisão estruturada, com risco e pontos de atenção para o revisor. Ela nunca aprova no lugar dele e nunca faz merge. O fechamento do ciclo é onde muitos projetos vazam valor: o código entra, mas a documentação fica para trás e a release vira arqueologia de PR. A review confere a entrega contra os critérios de aceite escritos lá no começo, fechando o fio com a descoberta. E a retro tem uma saída formal: se o mesmo atrito apareceu de novo, ele vira história de melhoria ou desce um degrau e vira skill, molde ou script. É o mesmo retorno composto dos casos de RPG, agora no ciclo Scrum. Transição: fecho da apresentação.

Perguntas?

O que foi construído não é uma coleção de prompts: é uma infraestrutura de colaboração entre pessoa e IA, com instruções versionadas, ferramentas determinísticas, moldes, portões e memória.
